# Архитектура проекта 64kwork

## Цель

Фреймворк для 64k intro на Linux/x86-64: финальный исполняемый файл ≤ 65536 байт
(как правило, после упаковщика), без CRT, с ручным управлением каждым байтом.

Принцип: **статически мы владеем только своим кодом**; тяжёлые библиотеки (libX11,
libGL/Mesa или драйвер) — динамические импорты, в теле 64k они стоят только
PLT-записи и строки в `.dynstr`.

## Слои

```
┌─────────────────────────────────────────────┐
│ intro (данные+код сцены, процедурная генерация)   │  ← будущий engine
├─────────────────────────────────────────────┤
│ intro_main: кадр-цикл, события, контекст GL  │  ← src/c/intro_main.c (сейчас база)
├─────────────────────────────────────────────┤
│ платформа: X11 (Xlib) + GLX, syscall-обёртки │  ← ручные прототипы, без заголовков
├─────────────────────────────────────────────┤
│ minicrt (план): свои malloc/строки/резолвер  │  ← замена libc для нашего кода
├─────────────────────────────────────────────┤
│ _start (src/asm/entry.asm)                   │  ← единственная точка входа
└─────────────────────────────────────────────┘
        ядро Linux (syscalls) + ld.so (динамические импорты)
```

- **entry.asm** — единственный ассемлерный файл запуска: обнуляет `rdi`/`rsi`
  (аргументы `intro_main`), вызывает его, `eax` → `SYS_exit`.
- **intro_main.c** — вся текущая платформа: `XOpenDisplay` → `glXChooseFBConfig` →
  `XCreateWindow` (1024×640) → `glXCreateContextAttribsARB` (GL 4.1 core) →
  цикл `XPending/XNextEvent` + рендер + `glXSwapBuffers` + `nanosleep` ~16 мс.
- Все типы X/GL — собственные opaque (`Display`, `GLXContext`, ...), все функции —
  ручные `extern`-прототипы. Единственный include — `<stddef.h>` (freestanding).
- `sys_write`/`nanosleep` — inline asm `syscall` (rax=1/35).

## Модель событий

Опрос неблокирующий: `XPending()` читает сокет X, `XNextEvent()` забирает событие
из уже заполненной очереди Xlib. `XCheck*`-функции сокет не читают — при прямом
DRI-рендерере (нет GLX-раундтрипов) события через них не доходят.
Обработчики: KeyPress(Esc/q) → выход; ClientMessage(WM_PROTOCOLS/WM_DELETE) → выход;
UnmapNotify/DestroyNotify → выход (случай композитора без WM_DELETE);
ConfigureNotify → ресайз viewport.

## ELF-раскладка (link.ld)

Интро-вариант: все секции идут вплотную в одном PT_LOAD (RWE), поэтому
страничный паддинг между сегментами отсутствует (экономия ~7.6 КБ на нашей базе).

Ключевые инварианты (нарушение = SIGSEGV при старте, см. AGENTS.md «Ловушки»):
- первый PT_LOAD: `p_offset=0`, покрывает ELF-заголовок+PT_LOAD/PT_DYNAMIC/PT_INTERP;
- `p_offset ≡ p_vaddr (mod 4096)` для каждого LOAD;
- program headers генерирует ld автоматически, порядок секций задаёт скрипт.

Состав бинарника (MinSizeRel, 5568 Б до упаковщика):

| часть | байт |
|---|---|
| наш код (.text) | 1218 |
| our data (.rodata: строки логов) | 448 |
| PLT + .rela.plt + .got.plt | 1240 |
| .dynsym + .dynstr + .gnu.hash + .dynamic + .interp | 1339 |
| заголовки ELF + PT_* + SHDR/SHSTRTAB | 1323 |

В импортах 24 символа (X11/GLX/GL), libc среди них нет.

## Размер и упаковщик

Бюджет меряется по MinSizeRel: `stat -c%s build-minsz/intro`.
До упаковщика — борьба с ELF (секции, строки, таблицы динамоки).
Упаковщик (UPX или самодельный elf-pack) — отдельный этап дорожной карты;
наша ELF-раскладка к нему заранее дружелюбна (один LOAD, нет RELRO-таблиц).

## Тесты
